# Session Transcript: design-agnostic-spec

## Session Overview
This session designed and implemented a language-agnostic detection and
messaging contract for `pkghooks`, following stage 001's research-only
output. Scope was revised mid-session after mpadge questioned whether
duplicating `vercel/detect-agent`'s detection data was necessary at all.

## Design Decisions Made

### Decision 1: Vendor detection data instead of re-deriving a schema
**Chosen:** Vendor `vercel/detect-agent`'s `agents.json` and
`agents.schema.json` verbatim, consumed as-is, rather than designing an
independent schema and hand-populated data file mirroring the same
content.
**Rationale:** mpadge identified that the initial plan (a bespoke schema
+ data file modeled on `agents.json`) duplicated data upstream already
maintains, creating a second artifact to keep in sync for no real benefit.
**Tradeoffs:** Ties the project to upstream's schema shape; any
project-specific fields (e.g. confidence) must live in a separate layer
rather than directly on each detection entry.
**Proposed by:** mpadge

### Decision 2: Confidence and intervention models as the sole novel layer
**Chosen:** Scope this stage down to two artifacts vendoring doesn't
provide: an abstract confidence-tiering model
(`high`/`medium`/`low`/`cooperative`) and an abstract intervention-point
model (`load_time`/`error_time`/`capability_gap_time`), both
language-neutral.
**Rationale:** These are `pkghooks`'s actual novel contribution;
`vercel/detect-agent` identifies which tool is calling but has no concept
of confidence or messaging behavior.
**Tradeoffs:** None significant — this narrows scope without losing
coverage, since the dropped schema/data tasks added no information beyond
what vendoring already supplies.
**Proposed by:** joint

### Decision 3: Automated sync via GitHub Action, PR-gated
**Chosen:** A weekly cron-triggered GitHub Action fetches upstream data,
diffs it against the vendored copy, and opens a pull request on any
change rather than auto-merging.
**Rationale:** Keeps the vendored copy current without manual polling,
while requiring human review before a detection-data change takes effect.
**Tradeoffs:** Introduces a dependency on a third-party action
(`peter-evans/create-pull-request`) and recurring CI usage.
**Proposed by:** mpadge

### Decision 4: Spec documents must stand alone from `specs/` stage history
**Chosen:** All references to specific stage numbers, task IDs, and
`specs/` paths were removed from every file under `agent-detect-spec/`,
with the underlying rationale rewritten in place rather than dropped.
**Rationale:** `agent-detect-spec/` is meant to be a durable, portable
contract; readers should not need the project's internal stage history to
understand it.
**Proposed by:** mpadge

## Tradeoffs Considered
- Independent schema vs. vendored data: vendoring won, since the
  independent-schema approach was found to add maintenance burden without
  adding coverage.
