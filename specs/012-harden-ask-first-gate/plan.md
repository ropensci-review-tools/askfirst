# Plan: harden-ask-first-gate

## Overview
Harden the ask-first gate: make askfirst_check_scenarios() halt at high confidence instead of merely informing, differentiate the directive line by severity, remove the workaround-as-menu-option framing from agent-hook guidance, and fix drift between the canonical agent-hooks/ source and the embedded installer copies.

## Context
This stage responds to `askfirst-advice.md`, a field report from an agent session using `dodgr` (an unrelated adopting package; its specifics are out of scope here — only the general askfirst-design issues it raised apply). The report described a concrete failure: `askfirst_check_scenarios()` printed its advisory message, the agent read it, and then proceeded to offer the user a menu with "implement the workaround" as one of two options — which the user correctly identified as not what "ask the user ... rather than implementing a workaround" means.

Prior stages already narrow the gap in adjacent ways, and this stage must not re-litigate them:
- **Stage 007** established a deliberate trust-boundary split: message text signalled by an adopting package (via `askfirst_signal()`) stays non-imperative/non-second-person because it is untrusted (spoofable by arbitrary package code); directive-strength instruction lives in the pre-loaded, trusted `agent-hooks/*/session_start.sh` context instead. This stage keeps that split — it strengthens the halting *mechanism* (which is not package-authored text, so the trust-boundary concern doesn't apply to it) and the *hook* text, not the R message text's tone.
- **Stage 010** restricted all agent-facing signals to `"high"` session confidence only (no false positives for human/low/medium-confidence callers). This stage's changes to `askfirst_check_scenarios()` only affect the existing `"high"`-confidence branch; the no-op-for-humans and no-op-below-high-confidence behavior is unchanged.
- **Stage 011** already made two partial fixes in direct response to the same underlying feedback: (a) a uniform `directive: ask-before-proceeding` line added to all four signal classes' structured prefix, and (b) a `session_start.sh` rule instructing the agent to mark "ask the user" as the recommended option when presenting a workaround-vs-ask choice. Re-reading the advice against the current code shows both were **partial** fixes: (a) still doesn't distinguish signals that actually halt execution from ones that don't, and (b) still frames the workaround as a selectable menu option (just a de-weighted one) rather than removing it from the choice set until the user has answered the permission question. This stage completes what 011 started rather than reversing it.

Design decisions for this stage (already confirmed with the user before writing this plan) are captured in three `AskUserQuestion` answers, each "Recommended" option accepted, plus two follow-up clarifications after the user reviewed the first draft of this plan:
1. `askfirst_check_scenarios()` should halt (`rlang::abort()`) at high confidence, the same mechanism `askfirst_capability_gap()` already uses, instead of `rlang::inform()`.
2. The `directive:` line should differ by actual severity rather than being the same string on all four signal classes. Follow-up: `askfirst_error_redirect` should also read `directive: stop-and-ask`, not `directive: notice` — confirmed below in Design Goal 2 and change 2.
3. `session_start.sh` rule 6 should stop instructing the agent to present a marked-recommended menu, and instead require the permission question be asked and answered before a workaround is offered as an option at all.

A fourth issue surfaced during investigation, independent of the advice doc's own numbered list: the installer that actually ships to real users has been silently stale since it was created. The user confirmed this must be fixed as part of this stage, not deferred — see Design Goal 4 and change 4.

## Design Goals
- **Make the "ask before proceeding" self-check an actual gate, not a message.** `askfirst_check_scenarios()` at high confidence must stop the calling agent's current tool call in a way it cannot read-and-continue past in the same turn, mirroring the halting behavior `askfirst_capability_gap()` already has for author-instrumented gaps.
- **Make the `directive:` field truthful.** An agent (or any downstream tooling) reading the structured prefix block should be able to tell, from the `directive:` value alone, whether the situation requires stopping to ask before proceeding. This is `stop-and-ask` for `capability_gap`, `scenario_check` (after change 1), and `error_redirect` — all three represent "ask the maintainer rather than working around it" situations, whether the halt comes from `askfirst_signal()`'s own `rlang::abort()` or (for `error_redirect`) from the real error it rides alongside. Only `notice` (load-time, nothing has gone wrong yet) stays advisory.
- **Stop asking hooks to soften the ask-first instruction into a UX preference.** Guidance text must not describe "implement the workaround" as any kind of selectable option — recommended, marked, or otherwise — until the upstream question has been posed to the user and answered. This applies to the scenario_check case specifically (the self-check with no author-anticipated example to match against), which is where the failure occurred.
- **Eliminate the drift between `agent-hooks/` and the shipped installer without reintroducing the coupling that motivated moving away from it.** The shipped installer (`tools/install-agent-hooks.sh`, symlinked as `bindings/r/inst/install-agent-hooks.sh`) embeds an independent, stale copy of the SessionStart/PostToolUse context — missing rules 5 and 6 that stage 011 added to `agent-hooks/claude/session_start.sh` and `agent-hooks/opencode/session_start.sh` (which are themselves byte-identical to each other). Real installs via the R package have never received stage 011's fix at all. Stage 007's own design-decisions.md (Decision 2) documents "a single source of truth avoids drift between R, Python, and future bindings" as the intended architecture, but a later commit in that same stage deliberately moved `tools/install-agent-hooks.sh` to a fully self-contained inline copy instead — because `tools/` is shared across every language binding present and future, and runtime filesystem discovery of `agent-hooks/` bakes in install-layout assumptions that may not hold for a non-R binding. This stage must close the drift gap *without* re-adding that runtime coupling — via a dev-time generation/verification step instead of a runtime filesystem lookup (see change 4).

## Proposed Approach

### 1. Halt `askfirst_check_scenarios()` at high confidence
- `bindings/r/R/scenarios.R`: change the high-confidence branch of `askfirst_check_scenarios()` from `askfirst_signal("askfirst_scenario_check", ..., call_stop = FALSE)` (implicit default) to `call_stop = TRUE`, passing the scenarios vector through as a condition field (consistent with how `askfirst_capability_gap()` already attaches its own fields) so the information remains inspectable via `tryCatch()`/condition handlers even though the call no longer returns normally on that path.
- Update the function's roxygen docs: it currently documents the high-confidence path as "also signals a non-fatal ... condition" and returning the scenario vector regardless of confidence. Both claims become inaccurate for the high-confidence branch and need rewriting to describe the halt, matching how `askfirst_capability_gap()`'s docs already describe its own halting behavior ("Unlike the load-time notice or error-time redirect, halting is the deliberate intent here").
- Leave the low/medium-confidence behavior (plain return, no condition) unchanged — out of scope, already correctly scoped by stage 010.

### 2. Differentiate the `directive:` line by severity
- `bindings/r/R/conditions.R`: in `askfirst_signal()`, replace the single hardcoded `directive_line <- "directive: ask-before-proceeding"` with a value chosen by signal class:
  - `askfirst_capability_gap` and `askfirst_scenario_check` (both halting, both `call_stop = TRUE` after change 1): `directive: stop-and-ask`
  - `askfirst_error_redirect`: also `directive: stop-and-ask` — even though this signal itself is still raised via `rlang::inform()` (`call_stop` stays `FALSE`; see `askfirst_error_handler()` in `init.R`), it only ever fires alongside a real error already propagating from the adopting package's own code, so the call has already halted by the time the agent sees it. The label describes the situation the agent is in, not `askfirst_signal()`'s own internal mechanism.
  - `askfirst_notice` only: `directive: notice` — the sole case where nothing has actually gone wrong or been detected yet, purely a load-time FYI.
- This can reuse the existing `type_map` lookup structure already present in `askfirst_signal()` rather than adding a second parallel map — extend it or add a sibling map keyed the same way.
- Update the roxygen docs on `askfirst_signal()` (which currently describe both a single uniform directive line, and describe `askfirst_error_redirect` simply as "non-fatal" without qualifying that it always accompanies an already-halting error) and any test in `test-conditions.R` (or wherever the prefix block is asserted) that hardcodes `"ask-before-proceeding"`.

### 3. Rework hook guidance to remove the workaround-as-menu-option framing
- `agent-hooks/claude/session_start.sh` and `agent-hooks/opencode/session_start.sh`: rewrite rule 6. Current text instructs marking "ask the user" as the recommended option in a two-option menu. New text should instead say something to the effect of: when `askfirst_check_scenarios()` (or any halting `stop-and-ask` signal) fires, the only immediate next step is to surface the upstream question to the user and wait for their answer — do not present, draft, or offer to implement a workaround as an option in the same turn.
- Adjust rule 5 (or fold into the same rule) if needed so the two rules read coherently together — rule 5 already establishes scenario lists are non-exhaustive; rule 6 should now build on the new `directive: stop-and-ask` vs `directive: notice` distinction from change 2, telling the agent that `stop-and-ask` signals gate further code-writing on that topic until the user responds, while `notice` signals do not.
- Keep the stage-007 constraint in mind: this text lives in the trusted hook context, not in package-authored message text, so directive-strength imperative phrasing here is fine and intentional.

### 4. Fix installer drift at the root cause
- Groundwork established during investigation of this stage: `bindings/r/inst/install-agent-hooks.sh` is a symlink to `tools/install-agent-hooks.sh` (confirmed via `ls -la`), so there is really only *one* installer script, not two — but `bindings/r/inst/agent-hooks` is *also* a symlink, to the top-level `agent-hooks/` directory, which means `agent-hooks/{claude,opencode}/session_start.sh` already ships alongside the installer in the installed R package tree. The installer does not need its own embedded copy of the hook text at all — it can read the file that already sits next to it.
- `git log` on `tools/install-agent-hooks.sh` shows the original stage-007 implementation actually did this: it resolved hooks from `"$SCRIPT_DIR/agent-hooks"` (installed-package layout) falling back to `"$SCRIPT_DIR/../agent-hooks"` (dev-tree layout, since `tools/` and `agent-hooks/` are siblings at the repo root), then simply `cp`'d the resolved file to the target. A later commit *in the same stage* replaced this with the inline heredoc. Per user clarification: this reversion was deliberate, not an oversight — `tools/` is shared, language-agnostic infrastructure meant to serve every future binding (currently only `bindings/r`, with `bindings/python`, `bindings/rust`, etc. anticipated per stage 007's own design-decisions.md), and making the installer's runtime behavior depend on filesystem-relative discovery of `agent-hooks/` bakes in an assumption about install-layout shape that may not hold for a binding whose packaging system doesn't preserve the same sibling-symlink structure R's does. **This stage must not reintroduce that runtime coupling.** `tools/install-agent-hooks.sh` stays self-contained and inline at runtime, with no filesystem lookup of `agent-hooks/` at install time.
- Instead, fix the drift with a *dev-time* generation step, which is itself generic (it only ever touches the shared `tools/` and `agent-hooks/` locations — never anything binding-specific, so it doesn't need to know R, Python, or Rust exist): add `tools/generate-install-hooks.sh`, run manually after any edit to `agent-hooks/claude/session_start.sh` or `agent-hooks/claude/post_tool_use.sh` (using the `claude/` copy as canonical source since `claude/` and `opencode/` are confirmed byte-identical), that regenerates the two heredoc blocks inside `tools/install-agent-hooks.sh`'s `write_session_start()`/`write_post_tool_use()` in place. Document the requirement to run it in a comment at the top of `tools/install-agent-hooks.sh` (mirroring the existing header comment there).
- Add a regression test that fails if `tools/install-agent-hooks.sh`'s embedded heredoc content ever diverges from `agent-hooks/claude/*.sh` again — e.g. a testthat test (or a plain shell test runnable independent of any one binding, since this check is itself generic infra and shouldn't live only under `bindings/r/tests/`) that extracts the heredoc block between the `SESSION_HOOK`/`POST_HOOK` markers and diffs it against the corresponding `agent-hooks/claude/*.sh` file byte-for-byte. This is what actually prevents the silent-drift failure mode from recurring — the generation script only helps if someone remembers to run it; the test catches it either way.

### 5. Update tests and docs
- `bindings/r/tests/testthat/test-scenarios.R`: the existing high-confidence test (`"askfirst_check_scenarios signals askfirst_scenario_check at high confidence"`) currently does `result <- askfirst_check_scenarios(...)` inside `withCallingHandlers()` with `invokeRestart("muffleMessage")`, and asserts `result` equals the scenario vector — this pattern assumes a non-fatal, resumable condition and will no longer work once the call aborts. Rewrite as an `expect_error()`/`tryCatch()`-style test on the condition, matching the pattern already used in `test-capability-gap.R` for `askfirst_capability_gap()`'s halting behavior.
- `bindings/r/vignettes/using-askfirst.Rmd`: section "3. What an agent sees: `askfirst_check_scenarios()`" currently says calling it "signals a non-fatal ... condition" at `"high"`/`"medium"` confidence — this needs updating both for the new halting behavior and for an existing, unrelated inaccuracy already present (the code only signals at `"high"`, not `"medium"`, per stage 010). Section "4. What your end users experience" also needs a line added for scenario_check's halting behavior, parallel to how it already describes `capability_gap`'s halt.

## Open Questions
All three questions raised in the first draft of this plan were resolved by the user before implementation:
- `askfirst_error_redirect` does move to `directive: stop-and-ask` (see Design Goal 2 and change 2).
- The installer drift is fixed at its root cause in this stage (restoring the copy-based, single-source-of-truth approach — see change 4), not deferred as a follow-up.
- Advice point 3 ("make the recommendation self-contained and actionable") remains intentionally excluded: the concrete example given was dodgr-specific, and the general capability it points at — authors writing specific, actionable scenario text — is already supported by the existing free-text `scenarios` argument to `askfirst_init()`.

No open questions remain blocking implementation. One thing to verify during implementation rather than decide now: whether `agent-hooks/claude/*.sh` and `agent-hooks/opencode/*.sh` are still byte-identical after change 3's edits (they were confirmed identical before this stage) — if any tool-specific wording need ever emerges, the installer's `HOOKS_DIR/$TOOL` resolution already supports per-tool divergence without further changes.
