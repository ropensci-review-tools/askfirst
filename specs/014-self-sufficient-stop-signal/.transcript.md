# Session Transcript: Self-Sufficient Stop Signal

## Session Overview
A field report describing an agent that read a `stop-and-ask` signal and offered a workaround as a menu option anyway prompted a review of stage 007/011's decision to keep `askfirst_signal()` message text neutral and non-imperative, with instruction strength confined to pre-loaded `agent-hooks/` context. The session decided to reopen that boundary and designed a self-sufficient hard-stop message shape, plus a companion mechanism to detect and nudge installation of missing/stale hooks.

## Design Decisions Made

### Decision 1: Reopen the message-text trust boundary
**Chosen:** `askfirst_signal()` message text now carries a fixed, imperative hard-stop block (delimiters plus a first-person-to-agent consequence statement) directly, for every `directive: stop-and-ask` signal, regardless of whether hooks are installed.
**Rationale:** Many sessions never have hooks installed or run with stale hooks predating any fix; the field report showed even the hooks-reinforced version failed. Message text must stop the agent on its own.
**Tradeoffs:** Reopens exposure to a deliberately spoofing adopting package, since no hook context vouches for the text's legitimacy without hooks installed.
**Proposed by:** mpadge, refined jointly

### Decision 2: Hard-stop strength is unconditional
**Chosen:** The hard-stop shape is emitted regardless of detected hook-installation status, rather than escalating only once hooks are confirmed current.
**Rationale:** Simpler, no runtime dependency between two otherwise-separate mechanisms; residual guardrail-rejection risk in the no-hooks case accepted as the lesser failure mode versus an unchallenged workaround.
**Proposed by:** mpadge

### Decision 3: Add hook-installation detection in the same stage
**Chosen:** A cross-language manifest and version-marker convention, checked once per session from `askfirst_init()`, nudges the human (not the agent) to install/update hooks when missing or stale.
**Rationale:** Complements message-text self-sufficiency by addressing the root cause — hooks not being installed — while keeping the check's shape portable to future non-R bindings.
**Proposed by:** mpadge

### Decision 4: Redirect the consequence text to the package's own developers
**Chosen:** The fixed consequence text tells the agent to direct the human to ask `{pkg}`'s developers, rather than asking the human to judge whether the capability belongs upstream.
**Rationale:** The human user typically has no basis to judge that; the package's developers do.
**Proposed by:** mpadge (explicit correction of the agent's first draft)

## Tradeoffs Considered
- Conditioning message strength on hook status (softer without hooks) vs. always-on: always-on chosen for simplicity, accepting residual risk.

## Open Questions
- Whether reopening the trust boundary needs a further anti-spoofing mechanism (signing, checksums) in a future stage — not addressed here.
