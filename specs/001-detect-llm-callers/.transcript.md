# Session Transcript: detect-llm-callers

## Session Overview
This stage researched how an R package could detect that it is being driven
by an LLM/AI coding agent rather than a human, and how it could deliver a
"redirect to the maintainer" message when the agent hits a bug or capability
gap. The plan and task breakdown were produced in a prior session; this
session executed all twelve research tasks and synthesized the findings into
`design.md`.

## Design Decisions Made

### Decision 1: Primary detection signal is a maintained env-var table
**Chosen:** Tool-specific environment variables (e.g. `CLAUDECODE`,
`CURSOR_AGENT`), checked once per session, as the primary signal; TTY
attachment and process ancestry as optional corroborating signals only.
**Rationale:** Env vars are set specifically by agent tools' own subprocess
spawning, giving high precision with no false positives on ordinary human
use, and require no cooperation from the target package's users. Direct
prior art exists in `vercel/detect-agent` and `unjs/std-env`, which use the
same approach.
**Tradeoffs:** Misses agent tools that reuse a human's existing terminal
without a distinct marker (e.g. GitHub Copilot Chat in VS Code, a known,
tracked gap upstream).
**Proposed by:** agent

### Decision 2: Three independent messaging intervention points
**Chosen:** Load-time (`.onLoad()`), error-time, and capability-gap-time,
confirming the plan's working hypothesis. First-call and every-call points
were explicitly rejected.
**Rationale:** Load-time is cheapest and most reliable; error-time reuses
R's condition system at no extra detection cost; capability-gap-time is
structurally distinct since nothing errors, so it needs its own hook.
Every-call was rejected for overhead and message-fatigue reasons.
**Tradeoffs:** Capability-gap detection is unavoidably opt-in — no
mechanical/heuristic alternative survived the false-positive constraint.
**Proposed by:** agent

### Decision 3: Detection logic structured as portable data, package stays R-only
**Chosen:** `pkghooks` ships as an R-only package, but its detection table
is structured as swappable data rather than logic entangled with R
integration code.
**Rationale:** The underlying signals are OS/process-level facts, not
R-specific; keeping them as data eases maintenance and leaves room for reuse
by a non-R implementation later without committing to one now.
**Tradeoffs:** None significant; this is a low-cost structuring choice.
**Proposed by:** agent

## Tradeoffs Considered
- Custom condition class vs. `message()`/`warning()`/`stop()` for message
  delivery: no single R primitive guarantees surfacing across all agent
  tool architectures, so delivery was layered — a structured condition
  class as primary, non-fatal at load time, reserving `stop()` for
  capability-gap/error-time interventions.
- `btw` package cooperation was evaluated as a complementary signal but
  deferred rather than adopted, since it requires an upstream change and
  covers only `btw`-mediated sessions.

## Open Questions
- Exact schema/contents of the env-var detection table and how to keep it
  in sync with external references like `vercel/detect-agent`.
- Naming of the default condition class hierarchy.
- Whether to pursue a `btw` upstream marker, and in what form.
- Whether parent-process ancestry detection ships as opt-in in v1.
- Whether detection confidence should be exposed to adopting packages.
- Testing strategy for environment-dependent detection logic.
