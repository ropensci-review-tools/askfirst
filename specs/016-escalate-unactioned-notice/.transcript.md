# Session Transcript: Escalate Unactioned Notice

## Session Overview
A field trial from the `askfirst-tests` harness showed an agent receiving a load-time `notice` and then writing a workaround without ever calling `askfirst_check_scenarios()` — the one action that raises the real `stop-and-ask` gate. This session designed and implemented a non-blocking `PostToolUse` escalation that closes that reachability gap, and, once a related state-storage concern surfaced mid-design, relocated all askfirst runtime state out of the project's working tree entirely.

## Design Decisions Made

### Decision 1: Non-blocking, untargeted escalation
**Chosen:** An unresolved notice triggers an escalating (not blocking) reminder on any subsequent file-editing tool call, regardless of whether the edit touches the flagged package.
**Rationale:** Keeps false-positive cost at "an extra line of text" rather than risking blocked, unrelated work; avoids a second content-scanning heuristic that could itself misfire.
**Tradeoffs:** Relies on the agent reading and acting on the reminder rather than forcing the check.
**Proposed by:** git-user

### Decision 2: Relocate all runtime state to a session-scoped tmp root
**Chosen:** `log`, `pending/`, and the new marker all move from the project's working tree to `${TMPDIR:-/tmp}/askfirst/<mangled-project-path>/`, derived independently by the R process and each hook script from the one value they share (the working directory). Mangling is a literal path transform, not a hash, prioritizing debuggability.
**Rationale:** These files are session-scoped and were sitting ungitignored in the project tree; a third marker family would have compounded a gap already deferred once.
**Tradeoffs:** No active pruning of leftover empty directories in this stage — left to normal tmp reaping.
**Proposed by:** joint

### Decision 3: Document, don't rebuild, the opencode gap
**Chosen:** Investigation found opencode's real plugin API is a JS/TS module registered via config, not a shell-script/stdin convention the existing hook files assume. Decision: document this precisely and leave the existing (likely non-functional) shell-script fallback in place, rather than building a real plugin in this stage.
**Rationale:** Matches prior precedent of shipping an explicitly-flagged unverified fallback rather than blocking on a larger, separate undertaking.
**Proposed by:** git-user
