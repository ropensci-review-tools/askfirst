# Session Transcript: scenario-check

## Session Overview
This session designed and implemented a new, independent `pkghooks`
mechanism for LLM/AI-agent callers who might be extending or duplicating a
package's functionality externally, rather than asking whether the
capability belongs in the package itself — addressing a case the existing
author-driven `flag_capability_gap()` cannot cover.

## Design Decisions Made

### Decision 1: Reject mechanical detection of in-progress workarounds
**Chosen:** No detection of monkey-patching/namespace-manipulation calls
(`assignInNamespace()`, `trace()`, etc.) was built.
**Rationale:** mpadge noted such calls are unlikely in practice, and more
fundamentally, the code an LLM writes to extend a package's functionality
typically lives entirely in the calling project and never touches the
package's namespace or triggers any observable R-level event — there is no
reliable execution-time trigger for this scenario at all.
**Proposed by:** mpadge

### Decision 2: An agent-invoked mechanism, not a system-triggered one
**Chosen:** A new exported function, `pkghooks_check_scenarios(pkg)`,
that the LLM calls on its own initiative at any point in a session,
combined with a strengthened load-time notice (generic instruction plus
author-supplied scenario list) that makes the tool discoverable from
session start.
**Rationale:** Since no mechanical trigger exists, the only viable
delivery path is (a) priming the LLM early with both the general principle
and concrete package-specific scenarios, and (b) giving it a callable tool
it can consult later, once the initial notice may have scrolled out of
context.
**Tradeoffs:** Entirely dependent on the LLM's own cooperation — nothing
forces the check to happen, unlike `flag_capability_gap()`'s halting
behavior for author-known gaps.
**Proposed by:** joint

### Decision 3: Fully additive; flag_capability_gap() unchanged
**Chosen:** No changes to `flag_capability_gap()`, `on_error` wrapping, or
any existing condition class.
**Proposed by:** mpadge

### Decision 4: Non-fatal severity
**Chosen:** `pkghooks_scenario_check` is signalled non-fatally (like
`pkghooks_notice`), never halting.
**Rationale:** Heuristic/self-assessed triggers carry more false-positive
risk than an author-confirmed gap; halting could break legitimate
workflows.
**Proposed by:** mpadge

### Decision 5: Confidence-gated, human-safe by default
**Chosen:** At `"low"` confidence, `pkghooks_check_scenarios()` returns the
scenario list as a plain invisible vector, with no condition signalled and
no "ask the human" framing.
**Rationale:** A human calling this deliberately doesn't need to be told
to ask themselves.
**Proposed by:** agent

## Tradeoffs Considered
- Mechanical detection vs. agent self-checking: mechanical detection was
  ruled out entirely as infeasible for this case, not merely deprioritized.
- Generic instruction always-included vs. author opt-out: decided
  always-included, centralizing wording the same way `pkghooks` already
  centralizes all other message delivery.
