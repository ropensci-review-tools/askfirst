# Session Transcript: namespace-hook-filenames

## Session Overview
mpadge reported that askfirst's Claude Code hook filenames
(`.claude/hooks/session_start.sh`, `post_tool_use.sh`,
`user_prompt_submit.sh`) are generic and conventional enough that another
tool could already occupy the same path, and that the installer's current
behavior would overwrite such a file. This stage renamed askfirst's hook
scripts to be namespaced, eliminating the collision.

## Design Decisions Made

### Decision 1: Namespace the hook script filenames rather than detect collisions by content
**Chosen:** Rename the three Claude Code hook scripts to
`askfirst-session-start.sh`/`askfirst-post-tool-use.sh`/
`askfirst-user-prompt-submit.sh`, instead of keeping generic names and
inspecting existing file content for an askfirst version marker before
overwriting.
**Rationale:** Namespacing removes the collision possibility at the root;
no other tool is likely to also choose an askfirst-prefixed name. A
content-detection approach would still leave a residual risk and added
complexity for ongoing maintenance.
**Tradeoffs:** Touches several files that hardcode the old filenames
(installer, manifest.json, hooks_status.R, tests, docs).
**Proposed by:** mpadge

### Decision 2: Verify filename-independence before proceeding, on two separate counts
**Chosen:** Before implementing, explicitly confirmed (a) Claude Code has
no filename-convention-based hook discovery — dispatch is purely via the
registered `command` string in `settings.json` — and (b) none of
askfirst's three hook scripts derive behavior from their own filename or
depend on cross-script filename references for correctness or ordering.
**Rationale:** mpadge specifically asked whether the scripts' names
implied a load-bearing temporal sequence that renaming could break. Both
counts were checked directly (official Claude Code hooks documentation
for the first; grepping all three scripts for `$0`/`basename`/cross-file
name references for the second) rather than assumed.
**Proposed by:** joint

### Decision 3: No migration path for existing installs
**Chosen:** Existing installs at the old generic filenames are not
migrated; users re-run the installer to get the new namespaced files.
**Rationale:** Kept the stage scoped to the rename itself; a fresh
install is sufficient and simpler than building cleanup logic for a
one-time filename change.
**Proposed by:** mpadge

## Tradeoffs Considered
- Content-based collision detection (keep generic names, inspect existing
  file content before overwriting) vs. namespacing: namespacing chosen for
  eliminating the risk entirely rather than mitigating it per-install.
