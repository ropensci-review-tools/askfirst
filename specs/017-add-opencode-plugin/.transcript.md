# Session Transcript: Add Opencode Plugin

## Session Overview
Following stage 016's finding that opencode's real plugin API doesn't match the shell-script hook convention `agent-hooks/opencode/*.sh` assumed, this session designed and implemented a real JS plugin achieving full parity with Claude Code's hook mechanism, then verified it end-to-end against a real, authenticated opencode session.

## Design Decisions Made

### Decision 1: Full parity scope, not a minimal canary-only stage
**Chosen:** Build all three hook equivalents now (context injection, non-blocking escalation, blocking gate) rather than deferring the blocking gate or doing verification-only work first.
**Rationale:** The blocking gate is the mechanism's strongest guarantee; deferring it would leave the fix incomplete.
**Proposed by:** git-user

### Decision 2: Plugins, not custom Tools
**Chosen:** Use opencode's Hooks/Plugin mechanism (intercepts existing tool calls automatically) rather than its Tools mechanism (agent-invoked, opt-in).
**Rationale:** Every behavior needed -- context injection, escalation, blocking -- requires watching the agent's own tool calls without depending on the agent choosing to invoke anything. A Tool-based implementation would reintroduce the exact reachability gap stage 016 fixed.
**Proposed by:** agent, confirmed by git-user

### Decision 3: `tool.execute.before` throw, not `permission.ask`, for blocking
**Chosen:** Block via throwing inside `tool.execute.before`, per opencode's own documented abort pattern.
**Rationale:** Confirmed live that this fires unconditionally on every tool call, whereas `permission.ask` only operates within opencode's existing permission-gating system -- narrower coverage.
**Proposed by:** joint (docs research + live verification)

### Decision 4: Remove legacy shell scripts, no fallback kept
**Chosen:** Delete `agent-hooks/opencode/*.sh` once the plugin mechanism was verified working, rather than keeping them as a defensive fallback.
**Rationale:** They were already confirmed non-functional against opencode's real API; keeping known-dead code adds no value.
**Proposed by:** git-user

## Tradeoffs Considered
- Exporting internal helper functions for easier unit testing vs. keeping the plugin's export surface minimal: rejected the former after discovering live that opencode's loader tries to invoke every exported binding as a plugin, so a mismatched second export hung plugin loading entirely. Tests exercise the real export indirectly instead.
