# Session Transcript: rename-to-askfirst

## Session Overview
This session renamed the R package (and every `pkghooks`-prefixed symbol)
to `askfirst`, after a naming brainstorm ruled out `askahuman` (an
existing, unrelated `github.com/askahuman` project) and settled on
`askfirst` as capturing the package's actual behavior.

## Design Decisions Made

### Decision 1: Proceed with askfirst despite an npm conflict
**Chosen:** Keep `askfirst` as the project name even though mpadge found
it already claimed on npm (unclaimed everywhere else checked).
**Rationale:** npm has heavy name-squatting for short, generic-sounding
words; it's normal practice to use a scoped/suffixed variant (e.g.
`askfirst-js`) in one registry once a binding for that ecosystem actually
exists, rather than compromising the primary name now for a language this
project hasn't built yet.
**Tradeoffs:** A future JS binding won't get the bare `askfirst` npm name.
**Proposed by:** joint

### Decision 2: In-repo rename only
**Chosen:** This stage renames package/function/class names, docs, and CI
references within the repo. The GitHub repository name and local working
directory are explicitly out of scope.
**Rationale:** mpadge will handle both separately; no git remote is
currently configured, so nothing external breaks in the meantime.
**Proposed by:** mpadge

### Decision 3: Historical stages left as an honest record
**Chosen:** `specs/001-detect-llm-callers` through
`specs/004-scenario-check` keep referring to `pkghooks`, unchanged. Only
the root `specs/design-decisions.md` (whose stated purpose is "Current
Architecture," continuously revised) was updated to describe `askfirst`.
**Rationale:** Consistent with this project's established precedent
(stage 002) of treating `specs/` as an honest historical record rather
than a document to retroactively clean up.
**Proposed by:** joint

### Decision 4: flag_capability_gap() renamed too, for API consistency
**Chosen:** `flag_capability_gap()` → `askfirst_capability_gap()`, even
though it never literally contained "pkghooks" and a pure text
substitution wouldn't have touched it.
**Rationale:** mpadge confirmed this explicitly, closing the one
inconsistency in the renamed package's exported API surface (every other
exported function already carried a prefix matching the package name).
**Proposed by:** mpadge

## Tradeoffs Considered
- Reconsidering the name entirely (given the npm conflict) vs. proceeding:
  proceeding won, since finding a name simultaneously available across
  every registry is a much harder bar than the actual near-term need.

## Open Questions
None outstanding. The GitHub repo/local directory rename and any future
CRAN-specific name-availability check are both explicitly deferred to
mpadge, not blocking this stage.
