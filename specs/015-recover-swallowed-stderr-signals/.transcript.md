# Session Transcript: recover-swallowed-stderr-signals

## Session Overview
A second field report described askfirst stop-and-ask signals being missed even when not discarded outright — buried in scrolling output, stripped by an agent's own ad hoc `grep` filtering, or acted on too late. The stage combined this with the original stderr-swallowing scope (`2>/dev/null`) into one design covering delivery redundancy, message format, persistent enforcement, and opt-in noise control.

## Design Decisions Made

### Decision 1: Stdout duplication scoped to stop-and-ask only
**Chosen:** Every `stop-and-ask` signal writes its full message to stdout in addition to the existing stderr delivery; `notice` signals are not duplicated.
**Rationale:** Notices are too frequent for stdout duplication to be tolerable; stop-and-ask is rare and halting, so redundancy there is cheap.
**Tradeoffs:** Notices remain exposed to the same swallowing failure mode as before, mitigated instead by the new opt-in silencing mechanism.
**Proposed by:** joint

### Decision 2: Persistent, actively-blocking sentinel over a passive log
**Chosen:** A `stop-and-ask` signal writes to `.askfirst/pending/`, and `post_tool_use.sh` blocks every subsequent tool call (exit code 2) while any pending file exists, cleared only by a new `user_prompt_submit.sh` hook at the next user turn.
**Rationale:** Addresses the field report's "delayed consequence" failure — a signal that fired several calls before it mattered, with no mechanism to re-surface it.
**Tradeoffs:** Requires a third hook type and installer/generator changes; opencode's actual blocking-hook support is undocumented, so its copy uses the Claude Code convention as an unverified fallback.
**Proposed by:** git-user

### Decision 3: Severity-first prefix and compact halt/resume tokens
**Chosen:** `askfirst::{lang}::{pkg}::{directive}` (directive first) with a `type:` line for the finer-grained class, and `<<<ASKFIRST:HALT>>>`/`<<<ASKFIRST:RESUME>>>` replacing prose delimiter lines.
**Rationale:** A prefix-anchored regex should catch severity on line one; compact tokens pattern-match more reliably than prose across repeated exposure.
**Proposed by:** git-user

## Tradeoffs Considered
- Prefixing every body line (not just bounding tokens) was considered and deferred as unnecessary complexity against `cli::format_inline()`'s reflow.

## Open Questions
- Whether `UserPromptSubmit`-triggered clearing is the right boundary versus an explicit acknowledgment action — not battle-tested.
- Whether opencode's plugin API genuinely supports blocking results at all, given no documented equivalent was found.
